# Maintained Switchyard core

Upstream: https://github.com/NVIDIA-NeMo/Switchyard

Maintained fork: https://github.com/eugenn/Switchyard

Develop server behavior, algorithms, APIs and server tests in the core repository.
The maintainer's checkout is the sibling `../NVIDIA`; contributors may use another
location with `scripts/update-switchyard.py --source /path/to/core`.

Keep topic branches focused so generally useful fixes can be proposed upstream.
Periodically merge upstream into the maintained core branch, resolve conflicts
there and run the affected crate tests. Preserve published commits and release
tags; do not rebase history already referenced by desktop releases.

## November 2026 desktop integration

The snapshot integrates NVIDIA commit `62e59f68620dbe725742d454b5797f886af371c0`.
The November 11 refresh includes the already-merged upstream fixes for Responses
streams, tool translation, Codex compaction history, target identity and routing
defaults. The source checkout's existing session-forwarding changes are preserved;
no new core changes were made during the desktop import.
The desktop keeps `plan_execute` as a saved preset identifier, but emits
`type = "stage_router"`. Its preset starts capable with `picker = "capable_first"`,
`confidence_threshold = 0.0`, `capable_hold_turns = 0`, and
`efficient_hold_turns = -1`. Successful tool signals can hand off to efficient;
critical failures can keep capable selected before handoff. Once the efficient
hold starts, later errors do not end it while that session state remains.
Clients must keep a stable session ID and send conversation/tool history.

Saved JSON profiles and generated TOML using the old edit-triggered route migrate
on restore. `planning_prompt` becomes `capable_system_prompt`; custom tool
semantics and other route fields survive. Judged handoff, `handoff_prompt`, and
`planner_reasoning_as_text = true` need manual review: Stage has no exact
replacement. These settings are retained and blocked from application rather
than silently discarded. New Plan → execute presets use the documented Stage
planning prompt.

### Thresholds

| Setting | Desktop preset | Meaning |
| --- | --- | --- |
| Stage `confidence_threshold` | `0.5` | Efficient-first: lower means easier escalation to capable. Capable-first: lower means easier offloading to efficient. |
| Plan → execute Stage threshold | `0.0` | Use Stage's capable-first recipe and permanent efficient hold after a switch. |
| Capability `base_threshold` | `0.5` | `p_solve >= threshold` selects efficient. This is an app starting preset, not a universal calibrated value. |
| Capability `threshold_step` | Omitted; server defaults to `0.0` | Adds a penalty for uncertain/unmatched/unsupported verdicts. `base_threshold + 2 * threshold_step` must be at most `1`. |
| Composite Stage threshold | `0.5` | Alias for `efficient_first_threshold`; capable-first behavior remains server-owned. |
| Decision judge `cutoff` | Not generated by the desktop | New server default `0.6`, compared strictly against `probabilities.capable`; it is not the LLM `base_threshold`. |

User-supplied native route bodies still replace the complete preset, preserving
custom thresholds, prompts and deadlines. The new tuning documentation contains
illustrative experiments, not measured defaults for this app's model pair; see
[core tuning](../vendor/switchyard/docs/tuning/index.md). The Rust desktop generates Jev decision-service configuration for Capability,
Custom and Composite routes. The new decision schema uses `choices` and
`apply_cutoff_to` instead of `candidates`, `criteria`, and `evidence`.

### Target identity and logs

The server now executes by target name. Two targets can share a provider model
and keep different prompts, reasoning efforts, or clients. The desktop permits
this, emits a separate judge target when a judge model is selected, and registers
each provider model only once with LiteLLM. Synthetic `judge-<model>` aliases are
no longer needed. This also preserves meaningful model names for the server's
new automatic Responses reasoning policy; the client leaves `responses_reasoning`
unset so the server chooses encrypted or plaintext replay per target.

Model statistics remain aggregated by provider ID; new server target breakdowns
are additive. Raw request details retain `target` and `reasoning_effort`. Routing
outcome envelopes are excluded from usage records so they do not inflate call
counts or produce unknown-model entries.

Validate with `desktop/scripts/build-switchyard.sh`, then run `cargo test --locked -p
switchyard-desktop-core` and `python3 scripts/verify-routing-parity.py` from
`desktop/`. The offline harness uses Rust-generated configurations and local
mocks, not the removed application. Public releases still require
`--verify --release --check-published`; see [release gates](releases.md).
